# 全系统业务闭环 E2E 测试路线图 (Full-Stack E2E Roadmap)

> **定位**：验证在真实多进程并发、HTTP/SSE 跨服务交互与人机协同闭环下的全业务链路可用性。
> **测试拓扑**：
> -  **`AegisFrontend`**（端口 `:5173`，React 控制台）
> -  **`AegisAgent`**（端口 `:8000`，LangGraph 状态编排宿主）
> -  **`AegisRAG`**（端口 `:8001`，语义检索微服务）
> -  **`Bash Shell Sandbox`**（端口 `:8002`，代码执行沙箱）

---

## 1. 核心端到端用例全景

| 场景编号 | 场景名称 | 触发条件 | 预期闭环结果 |
| :---: | :--- | :--- | :--- |
| **E2E-01** | **标准研发任务自主闭环** | 用户提交：“实现 C 语言单向链表反转函数并测试” | 检索现有代码 -> 制定计划 -> 写入代码 -> 沙箱单测编译通过 -> 前端呈现交付产物 |
| **E2E-02** | **越级高危动作与 HITL 审批闭环** | 任务执行中模型生成 `git push` 或跨目录写操作 | 触发 `interrupt()` 挂起 -> SSE 推送 -> 前端卡片交互 -> 后端恢复 -> 状态回填续跑 |
| **E2E-03** | **长会话多轮迭代与上下文治理** | 同一 Session 内连续派发 10+ 轮任务，日志累积超限 | `tiktoken` 实时计费 -> 水位计黄色预警 -> 原子对安全裁剪与滚动摘要 -> 杜绝 400 溢出 |
| **E2E-04** | **沙箱物理资源配额与熔断防御** | 代码运行中发生无限循环 `while(1)` 或内存超限 | Linux `setrlimit` 内存硬顶拦截 -> 沙箱超时硬杀 -> 错误信息安全回填模型调整 |

## 2. 核心场景演练时序

### 2.1 E2E-01：标准开发自主交付时序
1. 前端输入控制台通过 `useTaskStore.submitTask` 发起请求；
2. Agent 网关三道安全闸门验证通过，创建任务 ID 并建立 SSE 长连接；
3. LangGraph 状态机启动，`planner` 拆解里程碑；
4. 状态机调用 `DelegateCodeSearchTool` 向 AegisRAG (`:8001/api/v1/retrieve`) 获取工程上下文；
5. `executor` 编写代码，通过沙箱工具写入工作区目录；
6. 沙箱工具执行 `gcc test.c && ./a.out`，验证返回 `exit_code: 0`；
7. `evaluator` 确认里程碑全部达标，图流转收敛至 `END`；
8. 前端时间线全部标绿，Monaco 编辑器自动激活显示新代码。

### 2.2 E2E-02：越级命令与人机审批交互时序
1. 模型生成超出工作区写权限的高危命令；
2. `permission.py` 判定违背基线，`tool_runner` 调用 `interrupt()` 挂起；
3. SSE 向前端推送 `waiting_for_approval` 事件及审批要素；
4. 前端渲染 `HitlApprovalCard`，阻塞常规输入；
5. 研发人员点击“批准本次”，前端向后端派发 `/approve?scope=once`；
6. 后端通过 `Command(resume=...)` 恢复图执行，高危命令安全派发，任务正常续跑。

## 3. 验收标准

- 全链路无未经处理的未捕获异常；
- 状态机事件 100% 能够映射到前端 UI 状态组件。
